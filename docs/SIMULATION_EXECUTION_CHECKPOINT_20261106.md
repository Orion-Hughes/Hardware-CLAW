## 下一步测试与实现顺序

不继续通过增加prompt条款来追求“纸面完整”。下一步用现有计划执行真实仿真，检验计划是否能操作、是否采到足够证据、判据是否可判定。

### 1. 先修一个已证实的通用阻碍

文件写入保留CRLF，外部变更检查却读取为LF，造成 `EXTERNAL_CHANGE` 假警报。原电位器任务现场保留；修复必须在通用文件层，覆盖LF/CRLF/混合换行和真正外部变更的回归，不直接修改案例文件以绕过检查。相关证据见[三任务报告](AGENT_E2E_BUDGET_1M_20261106.md)。此修复尚未实施。

### 2. 程序执行已经生成的计划

首个目标使用已有摇杆串口工程，避免屏幕/机械角度观测成为前置条件。复用现有`wokwi_mcp.inspect`执行器与官方MCP能力，不再造一套底层连接。

- 执行前绑定project_id、revision、源码/构建标识和plan hash；有当前编译产物才运行。旧计划不能执行在已变化工程上。
- 程序重新校验事件并转换actions；从一个场景开始，完整执行“启动→设置输入/等待/读取→停止”。同场景保持同一会话，不能因分批重启丢失状态；不同场景独立会话。
- Agent提供测试意图，程序负责顺序、路径、版本、预算和清理。保留原计划，不临场无记录地改步骤；修改计划产生新版本。
- 取消、超时、工具错误必须保存已取得的证据并清理会话，不能进入无界重试。

### 3. 把证据交还Agent3分析

每次运行保存scene/test ID、event/action index、实际操作参数、宿主时间、原始响应、串口日志及可用的pin/VCD证据。实际有仿真时间再单独记录，不能把宿主等待冒充精确仿真时间。已有适配器能保留响应文件和哈希，新增执行报告负责关联到计划和场景。

Agent3以“原需求＋该场景计划＋实际证据＋工具状态”给出逐项判断，每项引用证据位置：

- `pass`：该项可观察判据有充分支持，不外推到整个系统。
- `fail`：证据明确违反该项要求。
- `inconclusive`：数据缺失、判据模糊、工具观测不到，不能硬判通过。
- `execution_error`：工具/环境/计划无法执行；与固件功能失败分开。

文字expected尚不是机器断言，因此早期判定应保留Agent分析与证据，不自动提升为宿主全工程verified。串口不能证明机械动作，瞬时pin不能证明PWM，设置回执不能证明固件收到输入。

### 4. 观察之后再增加一次有限修正

先至少跑通一个场景的取证与报告，再扩展全部场景。发现问题时区分计划本身、工具环境与固件：计划错误回到规划；固件问题交回generation，不让执行器修改源码。第一轮可只输出修改建议供检查，之后再接“修正→重新编译→重新规划/执行”的有限循环。

追加测试应覆盖正常取证、控件/通道错误、无串口或空数据、超时取消、版本过期、证据与场景绑定，以及不足证据不判pass。用软件fixture检验取消/异常等机制，用真实工程检验实际操作和观测，不能相互替代。
