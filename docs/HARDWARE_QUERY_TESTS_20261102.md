# 硬件双工具接口与真实查询记录

日期：2026-11-02。只读资料测试，不生成工程、不编译、不运行Wokwi、不验证实物。接口改造基于当前回退版本，未提交Git。

## 接口变化

- Agent只注册两个硬件工具：search_hardware和read_hardware。总工具数17；查询模式4个工具，生成模式17个。
- search_hardware返回选型需要的功能、输入输出、接口、引脚资源、约束和缺口。
- read_hardware一次传入1–8个硬件ID，自动读取卡中load=essential的基础资料，并带模型定义、驱动元数据、限定平台配置。共享原文和平台配置按ref去重。
- load=reference的扩展资料只列入口；用同一工具的references补读，不重复基础原文和平台配置。
- 当时整个JSON数据预算默认56000、最大60000字符。文件不截断，超预算为omitted；损坏原文为error；可选未读文件为reference。complete只表示本次选定资料完整返回。2026-11-05最大值已改为120000，并加入缺项/续读指引；当前接口见[读取服务说明](../LangChain/hardware_claw/catalog/README.md)，下方历史测试数据保持原样。
- 旧get_hardware_info/read_hardware_documents包装保留内部兼容与旧测试，未注册给Agent。工程服务继续使用兼容profile，无第二套磁盘资料。
- 同步更新System Prompt和hardware_selection/wokwi_generation技能。未加入阶段调度、子Agent或单工程特例。

连接卡中必读范围由维护者明确设置，不在运行中联网决定。API头文件和必要Wokwi说明优先；完整例程、实现源码及大网页通常为扩展参考。多器件较大组合仍可能需要一次补读，例如显示驱动的完整绘图库头文件。不能保证任意组合一次装入预算。

## 真实API查询

使用项目现有create_model和execute_turn，即与应用相同的LangChain Agent及运行时。模型配置为deepseek-flash，thinking关闭，输出上限1800。测试进程临时限制每轮6次LLM调用、12次工具调用、180秒，不改变应用生产预算。模型回调在累计已报告token达到60000后阻止该测试继续发起请求；单次请求仍可能越过该阈值。实际未触及限制。

### 第一次：DHT22

问题：请查阅本地DHT22的使用资料，说明功能、接口、初始化与读取API、采样约束和缺口，只做资料查询。

模型同一响应中调用两次search_hardware（DHT22和DHT），再调用一次read_hardware。原文提供了DHTesp初始化、显式型号、读取方法、采样周期及实物缺口。发现重复同义词搜索后，在通用Prompt/选型Skill中加入“同目标先用一个关键词，结果不足再换词；不同器件可并行”的规则。

### 第二次：组合查询

问题：用现有ESP32-S3通过摇杆控制SG90，从本地选型并说明接线接口、关键API、依赖和未验证项，不生成工程。

模型一次响应并行搜索三类器件，随后一次read_hardware读取三个ID，无额外逐器件查询。共同平台与说明只返回一次。

发现解释缺陷：回答引用Wokwi摇杆Arduino示例中的512/1023值，却未明确区分所选Arduino-ESP32框架的默认ADC分辨率；当地esp32-hal-adc.h明确写默认12位。资料已提供，模型仍可能套用示例范围。这不是接口读取失败，也不能当作完整正确答案。

改动只在所有硬件共用的guidance/usage-boundaries.md：要求示例数值、单位、分辨率、时序和默认值先核对目标平台；未给摇杆或该项目加入固定数值补丁。

### 第三次：同问题复查

相同自然语言问题，仍为三类搜索加一次批量读取；回答没有再套用512/1023值，提到了analogReadResolution及未标定ADC范围。这是单次观测，不能证明所有后续回答均正确，也未验证程序生成、实际ADC读数或舵机运行。

没有进行旧版/新版同模型重复采样的A/B成本实验，因此不声称已量化降低token百分比。当前证据支持“多个硬件资料可由一次读取返回”，不支持“彻底消除重复查询”。

## 后续预算修复（2026-11-02）

用户实际查询六器件时，返回体最终达到56247字符，超过56000预算，导致整批RESULT_TOO_LARGE。原因是先前装入原文后，后续文件的哈希、长度及错误元数据仍会增长。

修复仅涉及bundles.py的装包顺序：先读取并确定所有选中文档的完整元数据和读取错误，再按完整JSON长度逐份装入原文；complete字段的长度变化也纳入检查。放不下的原文仍返回omitted，索引本身超过预算才报RESULT_TOO_LARGE。未提高预算、未改变查询策略、跨轮历史或阶段设置。

原六器件请求离线复测返回execution_status=ok、complete=false，数据55672字符，8份原文included、10份omitted。新增通用内存fixture测试覆盖后续哈希/错误增长、JSON转义字符、刚好装满/差一个字符、补读，以及纯元数据超限；不依赖该六器件组合作为生产例外。此次未调用LLM API。
