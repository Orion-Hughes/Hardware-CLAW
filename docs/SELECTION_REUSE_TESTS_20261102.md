# 增量选型：实现与测试（2026-11-02）

修改前基线已提交并上传：`902d637`，分支 `codex/selection-reuse-20261102`。基线范围见[保存说明](versions/20261102-selection-baseline.md)。本次后续提交实现“沿用已接受选型，只读取新增/失效器件，并检查新旧组合”。不是固件生成或硬件功能验证。

## 实现范围

- 宿主从同一任务的最新completed选型和匹配的详细记录恢复来源证据；普通聊天描述和跨任务记录不能授予复用资格。
- 阶段开始时本地检查来源哈希、器件登记和模型映射，按受影响器件失效；无关目录变化不强制全部重读。旧记录可从真实工具事件恢复，但不修改旧记录。
- 传给子Agent的accepted_selection包含已确认需求、决策、精简器件/平台事实和来源引用，不包含整包API原文。新增器件正常查询；旧器件重复selection读取被拦截为复用提示，仍允许usage定向查证。
- 增量completed必须有覆盖最终器件的兼容性分析：需求、接口、资源、供电范围、平台。删除/替换旧器件须明确ID和理由；冲突先局部调整，无法满足才重选或阻塞。
- 完整证据快照留在阶段详细记录，主Agent只得到交接。失败不覆盖已接受方案；selection_update标识本次是否applied及读取、复用、移除记录。
- 没有加入特定工程的答案、驱动补丁或专用优化。

## 真实API测试

以下均通过真实主Agent委派选型子Agent，使用当前配置的DeepSeek提供方。每次均记录完整返回用量。追加屏幕测试把已有真实成功选型的交接/工具证据复制到隔离测试数据库，未改动原用户聊天；并非虚构fixture选型。另一个组合从空任务开始。

耗时为各轮记录的墙钟时间之和，不是单次调用延迟。调用次数为收到用量的模型响应数，不是工具数。未根据token自行推算人民币费用。

原用户“用库里的屏幕”一轮曾消耗180,962 tokens、16次调用、56.42秒；本次55,234 tokens降低约69.5%。这是单个案例的观察，测试没有回放完整原主聊天，不能视为严格A/B或长期平均节省率。复用包仍需作为上下文发送给API；并未让API获得跨调用内存。

屏幕追加报告还出现GPIO合计不一致：分项为屏幕5路、摇杆1路、DHT1路，文字却写约6路；不能因completed就把其兼容性分析当成正确的硬件验收。原始错误保留，没有人工改写模型交接。

摄像头测试后检查数据库：latest.selection仍为上一轮已接受交接，latest_attempts.selection记录本次blocked；没有移除旧器件或把摄像头加入已接受选型。这证明该次失败保留机制生效，不证明所有冲突都能自动修复。

## 已知边界及下一步

- 两次冷启动组合均失败于结构化报告JSON，错误存于invalid_tool_calls，现有流程以MISSING_REPORT结束。通用提示词提醒未解决；下一步需单独处理有预算约束的格式反馈/重提机制，不能用人工补引号或绕过Schema伪造成功。本轮未继续付费重试。
- 兼容性五项是模型资料级分析；宿主核验覆盖与状态，不核验所有算术、引脚或语义断言。尚未证明局部替换/整体重选在真实硬件冲突下成功。
- 证据来源在阶段开始核验；运行中并发修改资料不在本次保障范围。没有可信旧记录时仍需读取。
- 最后只增加宿主applied标志及失败移除统计保护，未再调用API；由离线测试验证。
- generation/verification子Agent仍未接入，本次没有生成、编译、仿真或烧录工程。当前版本可验收增量选型机制，不能称完整稳定的多阶段开发系统。

## 手动验收

网页进入`/coordinator`，先只做选型；同一对话追加一个器件。观察子Agent是否只查询新增项，交接是否保留旧ID并说明整体兼容性。也可在已有协调模式对话中追加硬件：有可信旧证据即复用。旧生成模式不受本次阶段适配器影响。
