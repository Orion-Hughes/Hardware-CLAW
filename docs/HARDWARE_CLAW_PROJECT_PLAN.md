## 1. 项目最终要求

### 1.1 项目定位

Hardware-CLAW 是一个运行在电脑端的 AI-agent-assisted 嵌入式硬件开发环境。用户通过文本界面描述 IoT 系统的传感、执行、联网、时序和 edge-AI 需求；系统将这些需求转换为结构化的嵌入式项目规格，并生成可编译、可仿真、可部署到真实 MCU 的完整工程。

一句话概括：

> 用户输入“我想要一个什么样的 IoT 系统”，Hardware-CLAW 输出“这个系统应该怎么做、代码是什么、电路怎么接、如何验证、失败后如何修正”。

### 1.2 核心功能要求

1. **文本需求接口**：接收自然语言或半结构化硬件需求描述。
2. **结构化项目描述**：将板卡、元件、接口、引脚、固件架构、库依赖、构建设置和验收测试整理为可供后续工具使用的数据；具体格式暂不固定，可随原型验证调整。
3. **固件生成**：生成 C/C++ 固件源码，优先支持 Arduino framework，后续视需要支持 ESP-IDF。
4. **Wokwi 工程生成**：生成 `diagram.json`、引脚连接、库依赖和可运行的仿真工程。
5. **命令行工具链集成**：集成编译、上传、仿真和串口监控工具。
6. **闭环修正**：读取编译错误、串口日志、仿真结果和测试结果，诊断失败原因并生成修正建议或修改代码。
7. **Edge-AI 部署顾问**：评估模型能否运行在目标 MCU 上，并给出量化、运行时、内存和性能方面的建议。
8. **系统评估**：构建代表性 IoT benchmark，量化评估易用性、规格正确性、构建成功率、修正有效性、可靠性和性能。

### 1.3 最终交付物

- 可运行的 Hardware-CLAW 文本接口。
- 结构化硬件/固件项目描述生成器（格式以最终实现为准）。
- MCU 固件与 Wokwi 工程生成器。
- compile-upload-monitor 工具链适配层。
- 基于反馈的自动或半自动修正循环。
- Edge-AI deployment advisor。
- Benchmark 数据集与定量评估结果。
- 最终报告、源码仓库和现场演示。

### 1.4 评估指标草案

| 维度 | 可测量指标示例 | 说明 |
|---|---|---|
| Usability | 用户完成任务时间、操作步数、满意度问卷 | 可先用小组内测试，后期扩大到志愿者 |
| Specification correctness | 引脚冲突数、缺失需求项、无效元件/接口组合数 | 需要人工或规则基线标注 |
| Build success | 一次生成后可编译率、自动修正后可编译率 | 应区分编译通过与行为正确 |
| Correction effectiveness | 修正成功率、平均迭代次数、是否引入新错误 | 必须记录每次失败与修复 |
| Reliability | 相同输入的重复运行稳定性、工具链失败恢复率 | Agent 输出需要缓存和复现实验设置 |
| Performance | 端到端耗时、生成耗时、编译耗时、仿真耗时、内存占用 | 分别统计 LLM、工具链和仿真耗时，并报告平均值、分位数和超时率 |
| Token efficiency | 输入 Token、输出 Token、总 Token、每次成功任务 Token、每轮修正 Token | 区分首次生成、验证和修正阶段，并比较不同模型和工作流 |
| Verification efficiency | 验证轮数、交叉验证 Token/耗时、无效重复验证次数 | 评估验证收益是否值得额外成本，避免无限验证 |
| Test effectiveness | 故意错误检出率、正确工程误报率、未覆盖/不支持项 | 用错误GPIO、常数读数、阈值反转等验证测试本身；不把不支持算通过 |
| Edge-AI advice accuracy | 内存/Flash/延迟估算误差、部署建议可用率 | 与真实板卡测量结果比较 |

保留单次Prompt生成作为基线，比较加入元件检索、执行反馈与有限修复后的质量、Token和耗时。统一需求、测试集和模型设置，报告各方案预算及首次/最终结果。复杂Agent不预设优于简单生成器；允许简化生成方式，但保留独立验证。性能记录区分模拟时间与墙钟时间。

### 1.6 导师近期指导

1. 评价体系除成功率和正确性外，还应统计 Token 消耗与各阶段耗时。
2. 最终综合验证可考虑设计一个板间通信系统，以覆盖多设备配置、通信协议、发送端与接收端固件生成、联合调试和真机测试。
3. 项目生成完成后，可尝试使用与生成模型不同的 LLM 进行交叉审查，但交叉验证不能替代编译、仿真、规则检查和真机测试。
4. 如何获得有效反馈、如何判断结果正确，是项目的关键研究问题，而不只是如何生成代码。
5. 验证和修正过程必须体现 Harness Engineering：设置状态、预算、超时、最大迭代次数和明确退出条件，避免无限验证、死循环、死锁或工具长期占用资源。

## 2. ESP-CLAW 与 Hardware-CLAW 的关系

### 2.1 ESP-CLAW 是什么

ESP-CLAW 是 Espressif 的设备端 Chat Coding AI agent framework。它的 agent runtime 主要运行在 ESP32 开发板上，通过聊天、事件、Lua 脚本和本地规则改变已经存在的设备行为。

### 2.2 Hardware-CLAW 与 ESP-CLAW 的核心区别

| 维度 | ESP-CLAW | Hardware-CLAW |
|---|---|---|
| 系统位置 | Agent 运行在 ESP32 设备端 | Agent 和工具链运行在电脑端 |
| 主要输入 | 用户聊天指令、设备事件 | 自然语言硬件项目需求 |
| 主要输出 | 改变已有设备行为、执行 Lua/技能 | 生成完整嵌入式工程和规格 |
| 硬件抽象 | 面向 ESP32 能力和事件 | 面向 board profile、元件、接口、引脚和固件架构 |
| 工具链 | 设备端能力调用 | 编译、上传、Wokwi 仿真、串口监控、测试 |
| 修正闭环 | 设备运行反馈 | 编译错误、串口日志、仿真结果、测试结果 |

简化理解：

> ESP-CLAW 是“用聊天控制一块已经存在的板子”；  
> Hardware-CLAW 是“用聊天生成、构建、仿真、调试一个嵌入式项目”。

### 2.3 为什么仍要复现 ESP-CLAW

ESP-CLAW 虽然与最终目标不同，但适合作为入门研究对象：

1. 观察 agent loop 如何组织。
2. 理解工具调用、能力抽象和事件路由。
3. 学习嵌入式设备上有限内存和不稳定连接下的设计取舍。
4. 借鉴其 harness、日志、技能和模块划分方式。
5. 为 Hardware-CLAW 的核心循环建立直觉。

当前ESP-Claw仅是早期学习对象和架构灵感来源，LangChain才是当前Agent实现框架。按具体问题阅读其工具调用与Core Loop即可；完整使用级复现不再作为Hardware-CLAW MVP前置条件。硬件生成仍需要内部多轮工具反馈，区别在任务目标与运行位置，不在是否使用多轮交互。

### 2.4 当前重点借鉴内容

当前对 ESP-Claw 的研究按以下顺序推进：

1. **Capability Runtime**：工具描述、JSON Schema、注册、Group、生命周期、LLM 可见性、权限、调用上下文和结果返回。
2. **Core Agent Loop**：LLM 如何选择工具、接收工具结果、继续推理，以及如何限制和终止迭代。
3. **Event Router**：区分需要 LLM 推理的任务与可以按确定性规则直接执行的任务。
4. **Skills**：向 LLM 提供硬件开发知识、工具用法和可靠的执行流程。
5. **Lua**：作为可选的设备端动态执行层研究，不作为 Hardware-CLAW 第一阶段的核心依赖。

Capability 是当前最直接的借鉴重点。Hardware-CLAW 应建立电脑端的统一工具接口，使 LLM 只能通过受控工具完成元件查询、引脚分配、工程生成、编译、Wokwi 仿真、上传、串口监控和 Edge-AI 评估。每个工具至少应包含：

- 清晰的名称和用途描述；
- 机器可校验的输入 Schema；
- 统一的调用上下文；
- 执行时参数验证和安全策略；
- 结构化成功、失败和日志返回；
- 可记录、可复现的调用信息。

已经阅读的 `cap_system` 展示了最小 Capability 的 descriptor、execute 和 Group 注册方式；`cap_files` 进一步展示了 JSON 参数解析、沙箱路径、读写权限、资源限制和错误处理。我们的实现应借鉴这些边界和接口设计，而不是直接复制其 ESP-IDF/C 代码。

### 2.5 其他项目研究后的取舍（2026-10-26）

- **Circuit Lab**：固定Prompt生成文件，宿主解析、有限编译、启动仿真并允许人工迭代。所查路径无独立硬件数据库、模型工具调用和自动行为验证闭环；适合作为轻量生成基线，不宜全盘否定或当作已验证的ESP32-S3端到端方案。
- **circuit-synth**：复用KiCad符号库，以Component/Pin/Net描述电路并导出工程；不只是画图，但元件选择、拓扑、参数设计仍需人或外部Agent决策。所查内部AI路径有关键词模板、连线TODO及缺失注册模块引用，不直接迁入其Agent框架。
- **我们的选择**：使用已有LangChain循环，重点建设硬件查询、受控工程操作和可靠验证；参考外部项目的具体机制，不以复刻其整体架构为目标。

证据、固定提交和详细限制见 [源码与验证研究入口](../references/research-20261026/README.md)。本轮未安装运行这些外部项目。

## 3. 候选方案：结构化项目描述

### 3.1 当前定位

此前讨论的 **Hardware Project IR** 只是一个候选的中间表示方案，当前不把它视为 Hardware-CLAW 的核心，也不预设它必须以独立、复杂或长期稳定的 IR 形式存在。随着 Capability、生成器、Wokwi 和编译闭环的实际开发，这套表示可能被简化、拆分、重命名，甚至被其他数据传递方式替代。

当前更合适的核心表述是：

> Hardware-CLAW 的核心是受控的 AI-Agent 工具系统，以及“需求理解—硬件配置—工程生成—编译/仿真—观察—修正”的可验证执行闭环。

结构化项目描述只是连接部分工具的候选数据载体，不是项目目标本身。

### 3.2 为什么暂时保留结构化描述

即使不把它作为核心，工具之间仍需要传递部分明确数据，例如：

- 目标开发板和 framework；
- 元件类型、数量和接口；
- 引脚分配与约束；
- 需要实现的行为；
- 固件和库依赖；
- Wokwi 生成参数；
- 编译、仿真和验收测试结果。

这些信息可以是一个 JSON 文档，也可以由多个小型模型、Capability 输入输出和项目文件共同表达。现阶段只为当前 MVP 定义最小字段，不提前固化完整通用 Schema。

### 3.3 临时示例

下面仅用于说明工具之间可能需要的数据，不代表最终格式：

示例中的 `serial_contains` 只作启动/输出冒烟检查，不能证明读数正确。正式行为验收应主动改变输入并检查响应；阈值、时限等条件另存版本化验收集。GPIO4与默认板型也不是采购板最终配置。

```json
{
  "target": {
    "board": "esp32-s3-devkitc-1",
    "framework": "arduino"
  },
  "components": [
    { "id": "sensor", "type": "dht22", "pins": { "data": 4 } },
    { "id": "display", "type": "ssd1306", "interface": "i2c" }
  ],
  "behavior": {
    "summary": "Read temperature and humidity and display them on the OLED",
    "interval_ms": 2000
  },
  "tests": [
    { "type": "build", "expect": "success" },
    { "type": "serial_contains", "value": "Temperature:" }
  ]
}
```

### 3.4 设计原则

1. 先让 DHT22 + OLED 基准项目端到端运行，再决定需要哪些字段。
2. 只保留被两个或更多模块实际使用的数据。
3. 每个 Capability 仍需有独立、明确的输入输出 Schema，不能依赖一个无限扩张的全局 IR。
4. 允许不同阶段使用不同的数据模型，例如需求描述、硬件配置、构建结果和测试结果。
5. 在闭环验证前，不把临时格式写成正式架构承诺。

### 3.5 候选生成物结构

```text
generated_project/
  project.json          # 可选的结构化项目描述，格式暂定
  sketch.ino
  diagram.json
  libraries.txt
  wokwi.toml
  test_suite_ref.json   # 引用独立维护的验收集ID/版本，不由生成Agent改写判定标准
  logs/
    build.log
    simulation.log
    serial.log
```

## 4. 技术路线

### 4.1 总体路线

```text
研究 ESP-CLAW 文档与源码
  -> Capability Runtime：工具定义、注册、权限、调用和返回
  -> Core Agent Loop：LLM 工具调用与多轮修正
  -> Event Router：确定性事件和 Agent 推理的分流
  -> Skills：硬件开发知识和工作流程
  -> 基于已有 LangChain create_agent 扩展受控工具与 Harness
  -> 完成硬件查询、工程管理、源码/电路生成、版本保存和交付
  -> 审查已有runner，验证编译、场景模板及正确/错误/超时路径
  -> 接入编译 / 仿真 / 串口反馈闭环
  -> 逐步扩展硬件选择、引脚分配和其他开发板
  -> 实现 Edge-AI advisor 与定量评估
```

结构化项目描述将在上述开发过程中按实际需要逐步形成，而不是作为必须先完成的独立核心阶段。

### 4.3 元件资料路线

复用上游库并建立本地补充层：Wokwi diagram-lint提供模拟type/pins/attrs等字段；wokwi-boards补模型映射；官方文档与part-tests补使用和测试参考；PlatformIO提供构建参数；厂家/模块资料补电气与驱动约束。KiCad符号库和modm设备资料作为后续扩展候选，不预设覆盖所有板卡。

本地补充逻辑信号、真实模块差异、GPIO约束、驱动版本与初始化、可控输入、可观测输出、测试模板适用范围、证据与验证状态。仿真端点合法不等于实物接线已确认。上游快照固定版本并保留许可，本地扩展不覆盖原始数据。

当前需保留的差异：采购屏为ST7789 240×320，而查到的board-st7789定义是第三方240×240模型；默认PlatformIO ESP32-S3 DevKitC配置是N8无PSRAM，不等同库存记录的N32R16V。不能用型号家族相同推断完全兼容。

### 4.4 测试规划、执行与反馈路线

测试是核心研究内容，分为三步：

1. **明确验收**：从需求提取预期行为、阈值比较、容差、响应时限与异常处理；关键歧义先澄清。预期不由生成代码当前表现决定。
2. **参数化测试**：开发者先实现传感器响应、阈值控制等通用模板；LLM选择模板、填写参数、建议边界案例。程序核对类型、端点及后端能力。特殊测试可由LLM起草，审阅后再纳入正式验收。
3. **确定性执行与判定**：独立适配器调用Wokwi CLI，采集串口、引脚和截图等证据；固定规则输出逐项结果，Agent据此修复。

建议运行输入为project_id、artifact_revision、test_suite_id，时限受工具策略控制。结果关联工件/测试版本、刺激、expected、observed、证据、退出码与耗时；区分通过、失败、超时、工具故障、不支持和证据不足。诊断假设与观察事实分开，修复Agent不能修改验收基准。

官方YAML场景为顺序动作执行，适合输入变化、数字输出、串口匹配和固定截图；数值容差、趋势、持续状态、复杂分支或随机测试需外层扩展。不能用一次电平检查证明全程无毛刺，也不能将网络日志到达时间当作模拟事件时间。

Wokwi CLI默认从本地工程连接远程Simulation API，不是完整离线引擎。需要核对token、网络和服务限制，同时设置模拟时间与宿主墙钟超时、进程树回收、有限重试和总预算。生成程序先建设；后续验证工具须独立验证正确工程通过、故意错误被检出、超时能退出，再接入Agent自我修正。

### 4.5 MVP 范围控制

第一阶段只固定三个场景：

1. 按钮控制 LED。
2. DHT22 温湿度采集 + OLED 显示。
3. 温度阈值报警 + LED / buzzer。

MVP 不做：

- 复杂 PCB 生成。
- 自动电路原理图导出。
- 多 Agent 复杂编排。
- 大规模并发硬件测试台。
- 过多开发板支持。
- 完全自动修 bug 的承诺。

MVP 的关键评价标准是：给定受限场景，系统能稳定生成规格、固件、Wokwi 工程，并能进入反馈闭环。

### 4.6 系统职责划分

| 知识与生成 | 来源明确的板卡/元件查询、最小连接数据、源码和Wokwi文件生成 |

### 4.7 验证、反馈与 Harness Engineering

生成工程不是任务终点。Hardware-CLAW 必须把“如何证明结果正确”作为独立模块设计。建议采用分层验证：

```text
结构与 Schema 检查
  -> 元件、接口、电压和引脚规则检查
  -> 项目文件完整性检查
  -> 编译检查
  -> Wokwi 仿真与串口断言
  -> 可选的第二 LLM 交叉审查
  -> 真机上传、串口和行为测试
```

不同 LLM 的交叉验证可用于发现遗漏、矛盾和可疑实现。例如模型 A 负责生成，模型 B 根据原始需求、生成物和测试结果进行审查。但模型间意见一致不等于工程正确，最终判断仍应优先依赖可执行测试和真实观测。

每次生成、验证和修正应记录：

- 使用的模型、提示词版本和工具版本；
- 输入、输出和总 Token；
- LLM 推理、工具执行、编译、仿真和总耗时；
- 验证结论及其证据来源；
- 修改内容、修改原因和前后结果；
- 当前迭代次数、剩余预算和终止原因。

Harness 至少需要以下保护：

- 每个工具独立超时；
- 整个任务的总时间、Token 和费用预算；
- 最大生成、验证和修正轮数；
- 状态机只允许合法状态转换；
- 同一错误或同一修改重复出现时停止；
- 对编译器、仿真器、串口和设备资源设置互斥与释放机制；
- 任务取消后清理子进程、串口句柄、临时锁和运行状态；
- 超时、死锁嫌疑、设备失联或无进展时安全退出并保留日志；
- 只有满足明确验收条件时才标记成功，预算耗尽不能被当作成功。

后期综合演示可考虑板间通信案例，例如一块开发板采集温湿度，另一块开发板接收数据并显示或触发执行器。该案例可以验证多板硬件选择、两套固件生成、通信接口配置、协议一致性、联合编译、真机通信和端到端验收，但不建议在单板 MVP 跑通前提前扩大范围。

## 9. 主要风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 范围过大 | 什么都想做，最后核心链路不稳定 | 固定三个 MVP 场景，每阶段必须有可演示输出 |
| LLM 输出不稳定 | 相同需求生成不同工程 | 引入 schema、validator、模板和确定性生成规则 |
| Wokwi 自动化限制 | 模型或场景能力不足、服务不可用 | 先做能力矩阵；不支持明确返回，范围调整需显式记录，不能静默删断言或记为通过 |
| 真机行为与仿真不一致 | 仿真通过但真机失败 | 保留仿真与真机两套验收测试，串口日志统一格式 |
| 编译环境差异 | 不同电脑结果不一致 | 使用容器或锁定依赖版本，记录完整构建日志 |
| 自动修正引入新错误 | 修一个错又出现另一个错 | 引入回归测试、修正预算和 diff 审查 |
| 验证循环无法退出 | 模型反复审查或修改同一问题，持续消耗 Token 和时间 | 设置状态机、最大轮数、无进展检测、总预算和明确退出条件 |
| 工具或设备资源死锁 | 编译、仿真、串口或上传任务相互等待，资源无法释放 | 工具超时、资源互斥、取消传播、清理机制和 watchdog |
| 交叉模型产生虚假共识 | 多个 LLM 同意但实际代码或电路仍然错误 | LLM 审查仅作补充，以规则、编译、仿真和真机测试为主要证据 |
| 板间通信案例范围过大 | 多板、协议和联合调试拖慢主线 | 先完成单板 MVP，再把双板通信作为后期综合验证案例 |
| Edge-AI advisor 难落地 | 模型估算误差大 | 先做 Flash/RAM/算力静态估算，再用少量真实模型校准 |
| 测试不能发现实际错误 | 只检查启动或串口PASS，错误工程也通过 | 冻结独立验收集，动态注入输入，验证GPIO错误、常数读数、阈值反转等负例 |
| 模拟时间不推进 | 网络/服务阻塞导致CLI不退出 | 额外设置宿主墙钟超时、取消传播和进程树回收 |
