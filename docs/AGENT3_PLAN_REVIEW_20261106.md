## 范围与结论

本次审查已有电位器计划，并对同一摇杆原工程独立运行两次 Agent3。两次使用相同代码、相同问题、新任务各自 300,000 reported tokens 预算，通过 Coordinator 调用真实 verification executor；没有调用主 Agent 模型，没有编译或仿真，也没有修改生产代码或生成工程。

两次均完成 JSON/Schema、通道与操作转换等静态校验。但语义审查发现可重复的测试设计问题，因此只能称为“规划流程完成”，不能称为“有效测试已验收”或“硬件功能通过”。

## 电位器计划：有覆盖，但判据需要修正

五个场景覆盖启动串口、正向变化、反向与保持、端点与保持、PWM 引脚观察。正反改变输入后读取日志的主体思路合理，也明确区分了目标角日志与真实轴角。

| 位置 | 发现 | 影响与建议 |
|---|---|---|
| T1 | 将精确启动文案和约 100ms 输出节奏纳入检查；状态接口“可读”被描述为运行证明 | 实现格式可以帮助解释日志，不应自动成为用户验收要求；必须检查返回的状态值，接口调用成功不代表会话运行 |
| T2 | 描述先保留 0/90/180 度，随后因 ADC/容差不确定退化为“只断言相对次序” | 不能把需求明确的目标范围删除。单调不减甚至可能允许恒定值；未知 ADC 绝对码与已要求的目标角范围应分别处理 |
| T2 | GPIO18 读数被部分描述为“确认串口连接” | 舵机 PWM 引脚的瞬时电平不能证明串口连接；该观察与目标不对应 |
| T3 | 用源码换算公式支持预期 | 源码可解释接口与时序，但公式本身也是待测对象，不能成为唯一正确性来源 |
| T4 | 5000ms 和 20000ms 各有连续两次清空式串口读取 | 第二次可能没有新日志，不能当作新的保持窗口；不应靠附加免责声明弥补缺少采集窗口 |
| T5 | 在 0、10、20 秒仅采三次引脚，期待高低两态 | 正常 PWM 也可能连续读低；不能把未读到高电平判失败。读到两态也只支持电平变化，不证明 PWM 频率、脉宽或机械运动 |
| gaps | 声称缺少 ADC 位宽，但源码明确设置 12 位 | 应区分已有配置与缺少量程标定，不能统称缺资料；“无屏幕”也可通过工程设计审查，不必强行归为运行时观测缺口 |

PWM 的 10 秒采样间隔恰为 50Hz 周期的整数倍，但这里是宿主调度而非精确仿真时间，不能声称一定锁定同一相位。真正问题是稀疏瞬时采样不足以排除正常脉冲。

## 摇杆第一次

8 条需求，7 个场景，5 个缺口，无重试。场景包含串口持续输出、居中基线、水平独立性、垂直独立性、斜向、回中保持、按键与消抖观察。正确避免把 Arduino 示例的 0/512/1023 直接套到 ESP32-S3 12 位 ADC。

主要问题：

1. **T4 重复清空读取**：10000ms 与 30000ms 各连读两次 serial。第二次不保证产生新样本，“冗余采证”不等于独立证据。
2. **T2 描述与证据不符**：不改变输入就无法排除常量伪造。事件文字承认这一点，但场景理由仍写“确认真实采样”，上下层结论不一致。
3. **方向判据弱化**：T3 把高低方向留给现场观察。资料实际上提供 x=+1 左/高、x=-1 右/低，y=+1 上/高、y=-1 下/低。绝对 ADC 码不确定不意味着方向也未知。只看“向某端变化”会漏掉反向实现。
4. **跨场景基线没有结构化传递**：T6 使用 T2 基线，T3/T4 也有此类文字引用；每例独立会话，当前产物没有明确的证据依赖/基线绑定。部分场景自己建立了基线，但不是所有场景均如此。
5. **消抖只能作弱观察**：代码每 100ms 输出，消抖窗口 30ms。日志没有抖动，不证明内部成功过滤毫秒级抖动；采样本身可能掩盖抖动。
6. **资料适用范围误读**：最后一条 gap 将网页鼠标/键盘的 partial movement 限制扩大到自动化能力。相同官方文档明确列出 x/y 为 [-1,1] float 自动化控制。应按接口适用范围判断；中间值的实际模拟行为仍需以后执行确认。

## 摇杆第二次

12 条需求，7 个场景，6 个缺口，两次局部重试。需求数量不同是拆分粒度变化，不能把数量增加视作覆盖增加。

### 两次重试

- 第 2 轮：T4 `channel` 写成字符串 `joy.x, joy.y`，实际契约只接受一个主通道。错误反馈列出可用通道；第 3 轮改为主通道 joy.x，组合操作留在描述与时间线内，校验通过。不是 JSON 语法错误。
- 第 10 轮：T7 有 21 事件，插入 12 次等待后共 33 操作，超过本地 32 上限。第 11 轮删除 55000ms 的一次串口读取，合并等待，最后 20 事件 + 11 等待 = 31 操作。错误反馈被有效采用。

32 上限属于当前项目的 MCP 操作包装层，不应宣称为 Wokwi 官方限制。本次两次规划没有被该上限最终阻断，但第二次为此增加了一轮完整上下文请求。

### 语义问题

1. **T6 消抖方法不成立**：称为“快速切换”，实际切换间隔 2–3 秒。正常按钮本来就应响应这种有效按压，不能要求它“不随每个边沿翻转”。默认模型 bounce 可能发生，但慢切换加低频日志仍不能可靠证明消抖有效。
2. **T4 先设置回中、同一计划时刻立即读取**：30000ms 设置两轴为 0 后马上读取，却期待“若干上报周期内”回中；计划没有安排该窗口。宿主调用耗时可能偶然提供间隔，但不能依赖它保证新数据。
3. **额外数字 pin 读取缺乏判别力**：T2/T4 读取模拟轴端口与 MCU 脚，解释为“确认连接/可读性”；瞬时数字电平不能证明模拟连线正确，增加操作与说明却不解决需求判定。
4. **缺口与已有能力矛盾**：gap 笼统说低有效行为不能用数字 pin 证明，而 T7 已计划读 SEL 未按高、按下低。电阻值、上拉强度和电压不能读取，但逻辑电平关系可以提供部分证据，应精确限定缺口。
5. **方向、容差、跨例基线仍不够明确**：部分时间线给出正确增大方向，场景层仍常使用“同一方向/以现场为准”。上下层判据需要一致。
6. **重复与长等待**：独立按键场景、所谓消抖场景、综合状态场景大量重复；部分场景等待到 40–60 秒，缺少需求或采样依据。执行时会放大仿真耗时和缓冲区截断风险。

### 为什么仍然用掉十几万 tokens

`verification.py` 为每个场景重新发送整个 shared：io_map、约束、全部文档、工程文件、原始需求等。时间线之间不是长聊天累积；是多个独立请求反复携带同一批原文。

第一次 T1 请求的 context 为 36,903 字符，documents 部分序列化后 28,730 字符（约 78%），project_files 3,348 字符、io_map 2,978 字符；系统 prompt + schema + 示例为 2,240 字符。这些是字符测量，不是精确分项 token 统计。

7 个时间线请求各约 12.7k 输入，而输出大多仅几百 tokens。首次测试时间线占总用量约 85.3%。要降用量，重点应是减少重复场景、按明确范围选择原文和降低无效重试，单纯压缩输出帮助有限。

## 下一步建议（本次未实施）

1. **先补通用时间线语义检查**：区分清空式读取与非破坏式读取；对于必须等待新样本的观察，要求声明响应窗口或同步条件。发现即时读取、同窗口重复清空、未定义的跨场景基线时一次性反馈问题清单。不要一概禁止同时间戳操作，基线 read 后 set 等顺序可以合理。
2. **明确证据能证明什么**：给观察声明分配依据、观察对象和证据边界。动态波形要求不能仅靠瞬时 pin；软件日志不能证明机械运动；缺少绝对标定不能删除已知方向和用户明确目标。
3. **让用例独立或显式声明依赖**：优先每例自行建立必要基线。需要跨例复用时记录结构化 evidence reference，不能只在中文里写“与 T2 比较”。
4. **减少重复，但不盲目删资料**：先合并相同输入序列覆盖的需求；时间线读取该场景相关器件、通道、源码接口与对应原文，保留来源和完整原文可追溯。不要用丢失依据的自由摘要替代。
5. **操作上限按执行机制处理**：既然 32 是本地包装约束，应评估是否可在同一仿真会话中由程序分批执行，保留整体时间/预算与中断控制，而非强迫模型为计数压缩掉有效观察。具体能否分批还需实现和验证。

当前优先级是测试方法可靠性，再是上下文减量。不要为这两个案例添加专用 prompt、skill、硬编码输出或驱动修补。
