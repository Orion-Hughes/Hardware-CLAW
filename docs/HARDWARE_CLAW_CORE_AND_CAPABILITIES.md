## 1. 项目定位与边界

Hardware-CLAW 是运行在电脑端、帮助用户开发嵌入式系统的 Agent 环境。主要产物是完整工程：固件源码、电路与接线描述、依赖和构建配置、测试及验证记录。

最终开发板运行生成的 C/C++ 固件，独立完成采样、判断和执行器控制。Agent 在电脑端负责开发、验证和修正。

需要区分两类多轮交互：

- 用户多轮对话：用于澄清需求和确认危险操作，不要求用户持续参与每次修正。
- Agent 内部多轮迭代：生成、编译、观察错误、修改、仿真、测试，是系统必须研究的闭环。

例如“每两秒读取温度，超过 30℃ 点亮红灯”应最终成为固件中的确定性逻辑；Agent 在开发阶段生成并验证该逻辑。

## 2. 核心组成

| 组成 | 责任 | 不应承担的责任 |
|---|---|---|
| Core Agent Loop | 管理任务状态、组织上下文、请求 LLM、处理工具调用、继续或结束任务 | 直接包含各类编译器、传感器及板卡驱动实现 |
| Capability Runtime | 工具注册、输入校验、权限控制、调用、结构化返回、日志 | 把模型输出无条件当作可执行指令 |
| Validation 与 Harness | 验收条件、证据检查、预算、超时、取消、隔离、恢复 | 只根据 LLM 的“已完成”宣告成功 |

Context Provider、Skills、项目状态和工具适配器支持以上核心。Hardware Project IR 仍只是候选数据载体，不是架构中心；初期可以用少量 JSON 字段和项目文件传递信息。

当前以LangChain `create_agent`驱动DeepSeek及工具，已连接工程生成、编译与仿真观测；继续复用现成循环，建设受控tools、资料与验证能力，不以重写通用Agent框架为目标。生成与执行链路可用不代表功能正确。ESP-Claw仅为学习对象和架构灵感来源，不是运行依赖；完整复现不是前置条件。

### 2.1 今天明确的取舍：生成可以简单，验证必须独立

- Circuit Lab 展示了“固定 Prompt → 工程文件 → 宿主解析、有限编译和启动”的最小路线，所查路径没有模型工具调用或自动行为验证闭环，但仍有工程处理与人工迭代价值。
- 保留单次 Prompt 生成作为实验基线和可用的简化方案；不因架构复杂就假设效果更好。即使简化生成器，也应保留独立检查与有限修正。
- circuit-synth 的可借鉴主干是元件/针脚/网络建模、复用 KiCad 库和工程导出；不仅是绘图，也不代表已自主完成元件选择、拓扑和参数设计。所查内部 Agent 路径有模板、连线 TODO 等限制。
- 设计决策、连接关系与图形布局分开处理。源码与 diagram 应消费同一份最小引脚分配，避免各自猜测。
- 详细源码证据与限制见 [本轮研究](../references/research-20261026/README.md)，不能把上游 Prompt 中的要求当成已执行的检查。

## 3. Core Loop 建议设计

### 3.1 运行流程

1. 接收需求，创建 project_id 和 run_id，记录目标、预算和工作目录。
2. 检查信息是否足够。对影响接线、电压、安全或验收的关键缺失项请求用户补充；其他假设显式记录。
3. 整理需求和验收条件，明确边界值、响应时限和容差；由测试规划选择模板并生成经审阅的版本化测试集，加载目标板卡、器件资料、相关 Skill 与已有项目状态。关键歧义先澄清，不从生成结果反推正确答案。
4. 调用 LLM，获得回答、澄清问题或工具调用请求。
5. Capability Runtime 校验参数、权限、路径和资源状态，执行允许的工具。
6. 保存工具结果与产物版本，将摘要和证据引用回填上下文。
7. 根据编译、仿真、规则检查、真机反馈继续修改，必要时请求用户介入。
8. 在验收通过、失败、取消、超时、预算耗尽或无进展时退出，输出证据和未解决项。

上述工程步骤不要求每一步都调用 LLM。已知命令、解析器、规则检查和测试断言由确定性程序执行，模型负责需求理解、方案选择与失败诊断等需要推理的环节。

### 3.2 通用运行状态与工程阶段分开

Core 可保留通用状态：QUEUED、BUILDING_CONTEXT、WAITING_LLM、RUNNING_TOOL、WAITING_USER、FINALIZING。

工具报告工程阶段：GENERATING、VALIDATING、COMPILING、SIMULATING、FLASHING、MONITORING、TESTING。这样增加新开发板或工具时，不必大幅修改 Core。

终态至少区分：

- SUCCEEDED：当前声明范围内的强制验收条件通过，并有对应证据。
- FAILED：确定失败，或在允许修正次数内无法解决。
- CANCELLED / TIMED_OUT / BUDGET_EXCEEDED：明确说明停止原因。
- NEEDS_USER：缺少信息、授权或实物操作，需要交接。

“模型输出最终答案”不等于“项目验收成功”。“仿真通过”也不能标记成“真机验证通过”。

### 3.3 退出与恢复机制

- 分别设置工具执行超时、LLM 请求超时、总任务截止时间。
- Wokwi 的模拟时间截止与宿主墙钟超时分别设置；模拟服务或网络停滞时，不能依赖模拟时间推进来退出。超时回收整个子进程树，保留诊断证据。
- 限制模型调用次数、工具轮数、修正次数、Token 和费用预算；持续检查预算，而非只在任务开始检查。
- 检测相同错误重复出现、文件未变化却重复测试等无进展情况。
- 取消或超时后终止并回收子进程，释放串口、设备锁和临时资源；不能只是停止等待结果。
- 同一串口和同一构建目录设置互斥访问；避免持有全局锁等待 LLM 或长时间外部进程。
- 区分工具基础设施故障与项目代码错误。缺失工具、无网络或权限失败不能无限触发代码改写。
- 重试前考虑副作用：只读查询可有限重试，烧录等操作不得盲目重复。
- 每轮修改保留版本或差异，可退回最近一次有效状态；最终附上未解决错误和日志位置。

ESP-Claw 的最大工具轮数值得借鉴，但单独的轮数上限无法覆盖工具阻塞、网络重试和所有死锁风险。

## 4. 值得借鉴的 ESP-Claw CAP

“保留”指迁移能力和接口思想，不是直接复制依赖 ESP-IDF 的实现。以下判断基于目前本地仓库的模块和工具描述。

| 模块 | 迁移用途 | 边界 |
|---|---|---|
| cap_files | 读取、创建、修改项目文件 | 限制项目目录，记录差异；删除和覆盖需保护 |
| cap_cli | 受控命令注册和执行接口 | 原版不是电脑端编译工具；需重新编写进程适配器，不开放任意 Shell |
| cap_boards | 板卡知识组织和 Skill 生成方式 | 当前由元数据生成板卡 Skill，不是通用选型、布线引擎 |
| cap_skill_mgr | 加载开发板、器件、开发流程说明 | 初期静态维护即可，不必让 Agent 自己发布或删除 Skill |
| cap_system | 设备状态与诊断思路 | 改为查询目标板和主机工具环境，不照搬查询板端 Agent 自身的逻辑 |

## 5. Hardware-CLAW 拟建设的 CAP

以下名称是接口草案，可按原型结果合并或拆分。并非每项都需要独立模块或独立 LLM。

| 能力 | 主要输入 | 主要输出 | 优先级 |
|---|---|---|---|
| get_board_info / get_component_info | 板卡或器件型号 | 引脚、电压、接口、资源、驱动指引、模拟映射、可控/可观测能力、未知项与来源版本 | MVP |
| read_file / write_file / apply_patch / list_files | 项目内路径和内容或差异 | 文件内容、版本或修改记录 | MVP |
| validate_connections | 元件与连接、目标板资料 | 冲突、兼容性问题、无法验证项 | MVP，先覆盖有限元件 |
| validate_project | 工程标识、需求和配置 | 文件完整性、依赖、引脚及配置一致性问题；可调用官方 diagram-lint | MVP |
| compile_project | 项目路径、目标板和构建配置 | 退出码、诊断、日志、固件及资源占用 | MVP |
| simulate_project | project_id、artifact_revision、test_suite_id；时限受工具策略约束 | 仿真执行状态、串口/引脚/截图证据、模拟及墙钟耗时 | MVP |
| evaluate_tests | 版本化验收条件及对应工件的执行证据 | 逐项 pass/fail/timeout/unsupported/证据不足，预期、实际和证据引用 | MVP |
| detect_devices | 允许探测的接口 | 设备和串口信息，含识别不确定性 | 真机阶段 |
| flash_firmware | 目标设备、固件和必要授权 | 烧录结果、产物标识和日志 | 真机阶段 |
| monitor_serial | 设备、波特率、采集时限 | 带时间信息的日志、断连和超时状态 | 真机阶段 |
| reset_device | 明确的设备标识和授权策略 | 复位执行状态 | 真机阶段，按需 |
| estimate_edge_ai | 模型、MCU、运行时和量化配置 | 内存/Flash/延迟估算、假设及部署建议 | 后续，但属于最终要求 |

长任务可采用统一 job_id，并提供 get_job_status、read_job_log、cancel_job；不必为每种工具分别实现一套任务管理。

代码和电路文件初期可由 LLM 配合文件工具生成。只有模板化或确定性转换确有价值时，再增加专门生成器；避免所有 CAP 都只是再次调用 LLM。

测试规划与测试执行分开：LLM 可选择模板、提出参数和补充场景，由程序检查模板参数与后端支持程度；运行工具只使用已确定的测试集版本。首期无需另建测试 Agent，也不强制新增一套通用测试语言。

## 6. Capability Runtime 的统一约定

每个工具需要明确：

- 名称、用途、输入 Schema、输出格式和版本。
- 调用上下文：project_id、run_id、工作目录、预算、权限、取消信号。
- 输入校验、路径限制、网络访问范围及副作用分类。
- 超时、输出大小限制、失败类型和重试策略。
- 可追踪日志、产物路径、文件哈希和执行耗时。

建议返回字段：status、error_code、summary、data、artifacts、log_ref、duration_ms、retryable。

其中通用 `status` 表示工具执行状态；`data.verdict` 或逐项 `checks[].status` 表示被测工程结论，避免混用。仿真报告还应关联 artifact_revision、test_suite_revision、expected、observed、evidence_ref、exit_code、wall_time_ms、simulation_time_ms。未知的时间/观测值留空，不伪造；LLM Token 由循环层记录。

必须区分“工具执行正常”与“被测项目通过”：例如 evaluate_tests 正常执行后，data 中仍可能包含多个失败用例；不能把工具返回成功当成项目成功。

文件修改、烧录和设备复位采用不同权限等级。工具选择与参数由模型提出，权限最终由程序执行，不由模型自行宣称获得。

## 7. 其他必要模块

| 模块 | 最小责任 |
|---|---|
| 文本界面 | 输入需求、展示进度、澄清、确认、取消和结果交接 |
| Context Provider | 选择相关板卡知识、项目状态和失败摘要，避免每轮塞入全部日志 |
| Skills / 知识库 | 保存工具用法、引脚约束、接线规则、测试流程，并标记来源和适用版本 |
| 项目与产物管理 | 保存需求、源码、电路、依赖、构建配置、固件和证据的对应版本 |
| 工具适配层 | 隔离 Arduino CLI、其他构建器、Wokwi 和串口工具的差异；实际选型需验证 |
| 日志与评估 | 记录模型版本、调用记录、Token、耗时、修正过程和最终结果 |

Wokwi 网页工程与自动化仿真入口所需文件可能不同，不能简单固定为下载得到的四个文件。自动化路径应验证电路描述、构建产物、配置和测试场景的实际要求，以及工具可用性和服务限制。

Wokwi CLI 默认读取本机工程并连接 Wokwi Simulation API，不是完整离线模拟引擎。接入需核对 token、网络、服务限制与版本。Wokwi Elements 只提供显示组件，不提供硬件行为仿真。

### 7.1 元件资料采用上游来源与本地补充层

- 优先复用 Wokwi diagram-lint 注册表的 type、pins、attrs、documented 等字段，以及 wokwi-boards 的内部模型映射；登记存在不等于全部行为已验证。
- 本地补充逻辑信号映射、模块级电气约束、GPIO占用、驱动/初始化、运行时 controls、观测渠道、测试模板适用条件、来源版本与模型差异。初始 attrs 不自动等同运行 controls。
- 数据按“真实模块/型号 → 逻辑信号 → 模拟端点 → 项目GPIO”关联。PlatformIO 构建参数、Wokwi board 类型与采购板型号分别记录。
- 当前查到的 ST7789 模型是第三方芯片实现的240×240显示板，不能直接等同采购的240×320模块。默认 PlatformIO S3 DevKitC 配置也不能直接等同 N32R16V。
- 上游快照与本地补充分别保存，保留提交和许可；不为扩大库而手工复制所有网页，也不将当前 JSON 格式固定为永久架构。

## 8. 如何判断项目正确

1. 需求检查：可观察行为与验收条件是否对应。
2. 静态检查：引脚、接口、依赖、文件与配置是否一致。
3. 编译检查：目标配置下能否构建，资源占用是否符合限制。
4. 仿真检查：输入变化时，输出是否满足测试条件。
5. 真机检查：接线、电源、串口、时序和实际器件行为是否符合预期。

仿真和规则检查不能覆盖全部电气风险；未知项应明确标记，不能默认安全。用户仍需完成真实接线等实物操作。

不同 LLM 可以交叉审查代码和遗漏项，但模型意见不是独立的物理证据。审查有次数和预算限制，发现的问题应尽量转换为可执行检查。修正过程不能为了通过而擅自放宽或删除原始验收条件。

### 8.1 测试职责：确定预期、生成场景、执行判定

1. **确定预期**：依据需求明确输入输出关系、阈值比较、响应时限、容差和错误行为。LLM 可发现歧义并提出建议，验收条件不能由当前生成结果决定。
2. **生成场景**：优先使用人工实现、可复用的测试模板。LLM 选择适用模板和填写参数，程序检查类型、范围、端点和后端能力。复杂新测试可由LLM起草，审阅后再纳入正式测试集。
3. **执行判定**：确定性程序生成/加载 YAML、调用CLI并解析证据。串口字符串匹配、数字引脚比较、截图比较各有边界；LLM 不直接裁定通过。

初期模板优先覆盖“传感器输入变化后读数响应”和“阈值控制”，随后扩展按钮、显示和持续运行。元件档案记录测试能力与适用条件，具体预期来自项目需求。例如“严格超过30°C报警”应覆盖25、30、31°C及下降恢复，不能把“大于”与“大于等于”混为一谈。

### 8.2 官方场景机制与扩展边界

官方 TestScenario 按顺序 await 执行固定动作：set-control、delay、wait-serial、write-serial、expect-pin、take-screenshot 等。所查执行器没有通用条件分支和循环语法；长固定序列可以由外层程序生成。

- wait-serial 是字节/字符串等待，不自动提供数值容差或实际读数诊断；需要保存并解析串口记录。
- expect-pin 检查某次数字电平，不证明整段时间没有脉冲，也不等于PWM/模拟量测量。
- take-screenshot 读取显示缓冲区并严格比较PNG；基准图需独立审阅，不能自动拿被测输出当正确答案。
- 趋势、响应时间、持续状态和随机测试需要外层测试程序及可靠观测；网络日志到达主机的时间不能直接当模拟事件时间。
- 不支持的测试返回 unsupported，观测不足返回 inconclusive，不能记为通过。若缩小范围，须明确更新需求/测试版本，不能静默删项。

### 8.3 反馈与测试自身的有效性

报告先记录输入刺激、expected、observed和证据，再给出候选原因；例如“31°C时灯仍为低电平”是事实，“比较符号错误”只是待验证假设。把断言失败、超时、工具故障、不支持及证据不足分开处理。

正式测试集独立于生成Agent可写区域，绑定项目与版本；修复阶段不可自行修改验收标准。可用另一LLM交叉审阅测试设计，但不以模型共识代替执行证据。

测试本身要经错误注入验证：正确工程通过；错误GPIO、常数读数、阈值反转、屏幕不刷新能被相应检查发现；无输出或死循环能超时退出。记录检出率、误判与未覆盖项，而不只统计“多少用例通过”。

## 9. 推进顺序

### 阶段 A：完成正式生成程序

沿已有LangChain核心实现硬件查询、工程创建、设计与文件操作、基本完整性检查、修订保存和交付。采用稳定模块边界与小型契约，保留澄清和失败恢复。DHT是首个用例而非硬编码的唯一目标；尚未运行的编译与仿真明确标not_run。

### 阶段 B：接入确定性验证工具

审查并复用现有Wokwi runner，在已建立的工程版本与结果契约上接入编译、lint、仿真及判定。传感器响应、阈值控制模板先独立验证正确、故意错误与超时三条路径，再开放给Agent；ST7789另做模型差异试验。

### 阶段 C：加入受控修复并扩展行为覆盖

由现有LangChain循环消费失败证据，修改后保存新修订，对同一验收版本重测。增加有限修复预算、无进展退出和边界测试；复用生成工具，不另建不受约束的外层循环。避免只评价编译成功率。

### 阶段 D：真机部署与综合案例

增加设备识别、授权烧录、串口采集和人工接线检查。板间通信可作为最终综合案例，但需先确认可用仿真能力；不能预设仿真支持全部多板通信场景。

### 阶段 E：最终要求与评估

实现 Edge-AI 部署顾问，比较生成模型和交叉审查策略，建立 benchmark，完成重复实验、报告和演示。

## 10. 评估与当前进度

评估至少记录：首次构建成功率、行为测试通过率、修正成功率、修正次数、失败类型、输入/输出 Token、LLM 与工具耗时、总耗时、超时率及每次成功任务成本。模型未提供 Token 数据时标记缺失或估算，不能记录为零。

在相同需求、验收集、模型设置与可比预算下比较：单次Prompt生成、加入硬件检索、加入执行反馈与有限修复。分别报告首次与预算内最终成功率、测试检错能力和成本；复杂Agent是否更好由结果决定。

当前基于已有讨论可确认：

- 已手动完成 Wokwi 温湿度读取与 OLED 显示案例。
- 已开展 ESP-Claw Capability 与 Core Loop 源码学习。
- 已明确电脑端开发 Agent 与板端独立固件的职责边界。
- 已有 LangChain/DeepSeek 最小只读板卡查询原型及用户提供的真实调用记录；还不是硬件生成或验收系统。

- 自动生成、自动编译仿真、闭环修正和真机自动化仍需逐步实现与验证。

近期目标：正式生成程序在明确支持范围内完成查询、设计、文件生成、修订与交付，并留下可追踪证据和未验证项；之后在同一结构上接入编译、仿真与有限修复。
