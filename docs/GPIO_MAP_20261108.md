# 程序生成 GPIO 表：实现与验证

记录日期：2026-11-08（运行记录使用 UTC）。分支：`codex/automatic-gpio-map`。

## 实现范围

`hardware_claw/projects/gpio_map.py` 从当前 `diagram.json`、已保存的硬件配置和来源锁定的上游 `board.json` 生成表格。Agent2 仍负责接线设计和固件；程序不重新分配 GPIO、不修补生成文件，也不让模型再提交一份表格 Schema。

数据流：保存设计 → scaffold 生成配置与电路 → 程序解析接线和板端点别名 → 将 GPIO 表作为工具结果交给 Agent2 → 编写固件 → 检查、编译。

每行包括主板实例、GPIO、板端点别名、连接端点、硬件 ID、信号名称、设计中的引脚常量和已登记的板级限制提示。仅列已连接 GPIO，不列未使用 GPIO 和电源脚。导线形成的分支和共享总线合并为网络；不假定电阻等器件内部导通。

当前 S3 来源明确映射 `TX→GPIO43`、`RX→GPIO44`，并非按数字端点猜测芯片引脚。缺少板级映射、未知端点、器件不匹配、设计与电路不一致时返回缺口。表格保留工程版本和电路、设计、硬件快照哈希及板卡来源。

报告位于 `workspace/<id>/.hwclaw/gpio_maps/v<version>/<report_sha256>.json/.md`。重新读取不改变源码、设计、修订和编译状态；历史报告保留。`get_project`、`scaffold_project`、`check_project_files` 以及电路写入返回全表；其他写入只返回当前报告引用。未新增模型工具或子阶段。

`ready` 只表示接线清单可以完整解析，**不表示固件引脚模式、电气兼容性或功能通过**。常量名称来自设计，不是对任意 C++ 程序的静态分析。生产构建仍只支持当前登记的 ESP32-S3 基线；多板解析测试不代表多板生成已经实现。

## 驱动版本

知识库保存的官方头文件、示例与说明供模型理解 API；实际编译需要 PlatformIO 获取对应实现库。当前 VS Code 流程已有固定版本约束：所选资料登记的库名称/版本 → 设计 dependencies → scaffold 的 `lib_deps = Name@version` → 编译器解析和构建。未登记名称/版本会拒绝，不允许自行改为 latest。

本次在 generation Skill 中明确这一行为，没有新增安装工具。固定版本不保证包管理器中一定能找到该版本；此前 `ESP32Servo@1.1.2` 包解析失败仍保留，不能称为已解决或直接归因为禁止联网。本次真实摇杆工程仅使用 Arduino core，不需要第三方驱动库，因此没有验证该舵机依赖问题。

## Agent3 后续接入建议（本次未实现）

后续更新：用户要求完整提供接线表，现已通过 `io_map.wiring` 接入，不精简字段；以下保留为当时的建议。实际实现与加入前后各两次测试见 [Agent3 IO 表对照](AGENT3_IO_TABLE_AB_20261108.md)。

建议提供，但应合并到 Agent3 已有的 `io_map`，不要把原电路、完整 GPIO 报告和另一份人工表一起重复发送。Agent3 当前 `io_map` 表达的是可设置的 controls、串口和可读取端点；GPIO 表表达的是板端点别名、MCU GPIO 与外设信号的对应关系，两者互补。

由程序基于同一修订生成精简的 `board_instance / gpio / peripheral endpoint / signal` 映射，保留版本、哈希和缺口，供 Agent3 选择刺激与观察通道。不要让 Agent2 在阶段摘要里重新抄写表格。固件修改或电路改变后重新派生，拒绝沿用过期映射。

GPIO 表不替代 controls 的范围/单位、固件串口协议、需求预期、时序信息与可观测性限制；数字引脚读取仍不能测电压、ADC 数值、PWM 参数或实际舵机角度。是否减少规划轮次和 token，需要接入后做真实对照测试；本轮未运行 Agent3。
