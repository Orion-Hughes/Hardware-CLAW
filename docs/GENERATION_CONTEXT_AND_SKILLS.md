资料库迁移更新：默认根目录已切换到`LangChain/hardware_library/`。get_driver_api索引从薄关联与原始library.properties派生，API正文来自锁定的上游原文，不再复制旧手写操作摘要。技能明确要求读取相关原文，索引本身不等于已阅读API。见[迁移验证记录](HARDWARE_LIBRARY_MIGRATION.md)。

更新：2026-10-29。参考本地ESP-Claw `345073d` 的组织方式，继续使用LangChain核心，不引入Lua运行时或示例专用业务模板。当前实验结果及预算见[进度总览](CURRENT_STATUS.md)。

## 当前执行路径

```text
CLI / Chainlit → runtime.execute_turn → build_agent
  → system.md + generation.md/query.md
  → GenerationContextMiddleware（每次模型调用前）
      本回合技能目录 + API入口 + 实际工具名 + 最新工程摘要
  → MessageViewMiddleware（仅缩小模型视图，原始工具证据保留）
  → TokenBudgetMiddleware（聊天协议输入预估、输出预留、累计usage校正）
  → 模型按需调用load_skill / get_hardware_info / get_driver_api
  → 模型设计并调用工程工具
  → 工具真实结果回填；下一轮重新读取工程版本和状态
  → 原有检查、编译、仿真、评估和交付判定
```

没有额外的模型规划调用；没有自动注入所有技能正文或所有驱动原文。用户需求/工程文本即使进入上下文仍为数据，不能覆盖系统规则。动态摘要每次从固定提示词重新组装，不把旧快照逐轮追加。

## 文件组织

| 位置（相对LangChain） | 职责 |
|---|---|
| `prompts/system.md` | 稳定职责、资料使用、通用约束 |
| `prompts/generation.md`、`query.md` | 明确区分有工程/无工程模式，不再字符串替换查询提示词 |
| `hardware_claw/context.py` | 技能目录按回合准备，工程摘要每次模型调用刷新；同步/异步调用均支持 |
| `hardware_claw/message_view.py` | 近期工具结果/技能/API保留，旧大结果和写入正文仅在模型视图中省略；记录前后字符量 |
| `hardware_claw/skill_catalog.py` | 技能包发现、元数据、参考资源和路径检查 |
| `hardware_claw/tools/skills.py` | load_skill工具 |
| `hardware_claw/catalog/driver_api.py` | 从已有driver_profile派生索引与原文引用 |
| `hardware_claw/tools/driver_api.py` | get_driver_api工具 |
| `skills/<id>/SKILL.md` | 5个现有技能的包入口 |
| `skills/<id>/references/*.md` | 需求、修改、兼容交付和固件设计的按需说明 |

技能与硬件资料分开：技能包提供通用方法，硬件/API原文由hardware_library提供；旧knowledge仅作归档。生产Agent不能通过这些工具写技能、知识库或运行任意脚本。

## 技能格式与接口

SKILL.md以`---`包围的JSON元数据开始，包含name、description、tool_groups和references。name匹配目录；引用只允许包内已登记Markdown；禁止路径越界、符号链接与Windows目录联接。无效包在目录中列出错误并跳过，读取失败不伪造空正文。

```json
{"skill_id":""}
{"skill_id":"firmware_and_observation"}
{"skill_id":"firmware_and_observation","reference":"references/firmware_design.md","offset":0,"limit":6000}
```

元数据用于发现与说明。tool_groups本阶段不隐藏工具，也不授予权限。当前没有技能自动安装/自修改、跨用户回合的正文缓存或动态能力激活机制。

固件技能明确要求先读API、设计状态与时序、处理资源和错误、保持设计/代码一致。多个行为组合时读取通用设计参考；简单任务不强行引入复杂状态机或RTOS。默认vscode流程与兼容源码交付说明已分开。

## 驱动/API入口

```json
{}
{"hardware_id":"搜索返回的ID"}
{"hardware_id":"搜索返回的ID","query":"函数名或章节关键词","limit":3000}
{"hardware_id":"搜索返回的ID","reference":"工具返回的已登记路径","offset":0,"limit":6000}
```

- 空hardware_id返回本地驱动索引，最多30条/页，offset按条目计数。
- 指定ID默认返回从薄关联派生的精简driver_profile、框架/依赖版本、12项分页原文目录、资料状态、缺失信息和来源哈希；detail=full可取完整配置。query字面检索该器件全部登记原文，片段带原文偏移/行号/哈希。具体用法仍读取足够的原文上下文。
- 原文仅接受该driver_profile登记的source_refs、example_refs及依赖source_ref。头文件名本身不授予文件读取权限，不能猜路径。
- 原文offset按字符计数，返回sha256、partial、next_offset；读多页不重复返回整个驱动配置。外部原文是参考数据，不是Agent指令。
- 全程离线；既不下载新资料，也不验证提供方库版本的运行兼容性。缺少API正文、未登记文件、blocked、metadata_only、unknown等均保留。
- 本地15个关联条目包含10个documented_not_tested、4个blocked、1个unreviewed，不等于15种器件都可生成。SSD1306条目仍为unreviewed，其资料入口不能替代尚未补齐的生成适配。

get_hardware_info现在默认compact，保留规格、映射和约束，减少重复路径与完整驱动列表；detail=full可取完整记录。已知硬件ID和函数时可直接检索原文，不强制再次读驱动索引。

## Context Provider范围

提供工程ID、交付模式、最新版本、设计版本、需求摘要、选中组件/依赖/实现方案、文件元信息、当前分阶段检查/构建/仿真状态及导出信息。保留stage_verdicts、构建复用版本及failure_kind；长需求与列表明确截断，详细设计由get_project读取；源码和长日志不会自动注入。

数据来自ProjectService：检查报告须匹配当前版本及检查器版本；编译记录仅在输入和安装环境身份匹配时可跨版本复用，并显式标明built_version/reused_from_version/cached。仿真和导出仍核验对应身份，不能因复用固件就判功能通过。摘要不绕过工具的版本检查、证据哈希校验或阶段门槛。

当前Provider没有从对话历史中提取并维护任务工作记忆。另有两层按轮数处理：`runtime.py`/`app.py`跨用户回合保留最近6轮已完成问答，不自动续传上回合工具链；`message_view.py`在单回合内主要按最近3组工具轮次保留正文。原始运行证据在磁盘上保留，不等于模型下一次会自动看到。

## 下一步：按任务与证据优先级组织上下文（规划，未实现）

扩展现有Context Provider及消息视图，不另起一个平行Agent。优先级是宿主选择上下文的元数据，不是LLM API标准的逐消息priority参数，也不改变用户文本、外部资料或工具结果的指令权限。

以可追溯的信息条目为单位，而非只给整条消息打分：

| 类别 | 应保留的内容 | 降级或更新依据 |
|---|---|---|
| 当前任务必需信息 | 当前请求、明确约束、工程/会话身份和当前版本 | 用户明确修改需求时建立来源可追踪的更新；不从模型总结推断需求已改变 |
| 未完成工作与证据 | 未解决错误、未评估观察、当前诊断需要的输入/输出/时间/证据片段 | 有对应的新结果或问题明确结束后降为摘要；未验证不得写成通过 |
| 当前实现需要的资料 | 所选器件约束、正在使用的驱动API和技能相关段落 | 实现切换、资料哈希变化或阶段结束时重新选取 |
| 已完成或过期内容 | 已解决故障、旧文件版本、重复资料、历史讨论 | 保留简短状态、原版本、来源哈希及重读位置，原始内容继续归档 |

建议每个条目至少记录来源消息/tool_call_id、工程及会话身份、版本/内容哈希、原文引用、状态、保留理由和大小估计；priority不代替来源可信度。旧证据可作为历史比较资料，但不能替当前版本作结论。不同问题可同时开放，第二次仿真超时不能挤掉仍未分析的第一次观察。

建议数据流：

```text
当前用户请求 + 工程真实状态 + 有来源的历史工作记忆 + 最新工具结果
  → 更新事实、版本和待处理事项，去重，保留不确定性
  → 按任务相关性、未解决状态、有效版本、信息大小选择原文片段/摘要/引用
  → 在单次输入预算内组装上下文；轮数仅作为辅助排序
  → 现有累计TokenBudgetMiddleware预检 → LLM → 工具 → 更新工作记忆
```

- 单次输入预算需计入system prompt和工具Schema，并留出输出空间；它与当前每轮累计500,000 tokens上限不同。高优先级也不代表无限保留全部日志。必需信息容纳不下时明确分阶段处理或报告限制，不能静默丢弃关键约束。
- 第一版由Python从已结构化的工程状态和工具结果提取事实、错误及证据引用，无需每轮额外调用摘要模型。开放式自然语言的意图、约束和问题关联不能靠通用字符串规则保证准确；应保留必要原文，若以后加入模型辅助摘要，须标明推断、校验来源并记录其成本。
- 工作记忆与当前对话及工程绑定，原始记录不变；应在截短聊天历史之前更新，也应保存失败/取消时已经取得的证据。不能只修改`build_view`而继续在入口处丢掉跨回合信息。持久化文件和接口尚未实现/定名。
- System Prompt继续表达稳定规则。工作记忆中的用户文本、日志和外部API仍是带来源的数据，不提升为系统指令。已有检查器及工具继续决定版本有效性、可执行性和验收状态。
- 上下文选择应记录选中/省略的条目、原因及大小，保持请求/工具结果配对。对稳定资料采用确定顺序、避免重复注入；缓存效果需看提供方usage，不能保证缩短上下文一定降低总费用。

验证先用本地历史回放和跨多种工具的机制测试：超过三轮仍保留未决证据、用户更新覆盖旧约束、旧版本不冒充当前、已解决内容降级、跨回合/失败恢复、预算与来源链不丢失。再比较真实API输入、缓存命中、重读次数、任务完成率和耗时。不能把字符缩短或离线规则正确等同于真实任务成功。
