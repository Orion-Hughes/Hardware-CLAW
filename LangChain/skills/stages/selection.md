# 选型阶段工作流程

1. 从用户需求提取输入、输出、交互、时序、仿真/实物范围、指定器件及禁止替代等约束。选型阶段不细化最终接线和固件实现；不要因缺少字体、GPIO、代码细节而无限追问。
2. 没有明确ID时用search_hardware查候选。关键词是AND匹配，优先短关键词或kind，不同类别可同批查询；不重复搜索同义词来凑结果。有明确ID直接读取。local足够则不扩大到upstream；上游模型存在不代表已有可用驱动适配。
3. 先继承accepted_selection中的有效旧器件及已确认约束，只对新增器件和invalidated器件调用read_hardware，view=selection；超过8个分批。它给出功能、I/O、资源要求、依赖、平台适用范围、仿真实物差异和资料目录。不要重读未变化的旧器件，不要在选型时批量加载全套API源码。
4. 核对需求覆盖、总线/资源需求、平台范围、模型映射、供电信息的适用范围和已知缺口。具体性能参数若不在选型视图里且决定方案，用read_hardware的view=usage和references补读登记的相应原文；usage不带references的整包编程资料读取在本阶段不开放。不为补齐所有参考文档而循环查询。补读仍不足就报告具体缺口。
5. 区分资料配置documented_not_tested与运行通过，区分owned、reference和simulation_variant。平台配置不能外推到其他板卡；仿真供电配置不能作为实物额定值。blocked/unreviewed/metadata_only不能作为无缺口的可生成方案。
6. 有旧方案时，对新旧组合填写compatibility五项说明：需求覆盖、接口、GPIO/总线资源、供电适用范围、驱动/构建平台。相容则合并选型；冲突则先局部修正，不行才重选。资源判断不能冒充最终引脚分配或仿真验证。输出全部保留和新增器件，移除项明确列出并解释。
7. 退出条件：需求已概括、所有所选硬件已由宿主继承或本轮读取、组合无已知阻碍、假设已披露后提交completed。后续是否继续由主Agent结合本轮请求决定。不要重复读取相同资料，不要求用户替程序提供已有本地资料。遇到不可解缺口及时提交blocked/needs_input。

交接保留需求、选型理由、关键约束、假设及来源引用。完整原文和工具记录由宿主保存，后续生成阶段按ID读取编程资料；主Agent不接收整包源码。
